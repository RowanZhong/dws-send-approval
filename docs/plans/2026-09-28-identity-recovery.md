# 已登录 DWS 的身份检测兼容修复

## 问题与证据

用户报告：OpenClaw 2026.7.1-2 已登录 DWS，安装已上线 main 版后，`/dws`、`/dws identity`、`/dws identity refresh` 无法进入助手；身份提示为“检测失败 / 缺少有效的组织、用户或授权应用 ID”。退出再登录后恢复。

已上线 main `fa07266a7f16acbcc817cc126123f1615b7c5a02` 与实际旧版 SDK、DWS 1.0.58 的复现结果：

- 正常的既有真实登录可以直接初始化并刷新，无需退出再登录。因此不是所有旧宿主或已有登录都失效。
- 在隔离目录用合成加密凭据构造“有效登录、profile 缺少 clientId”，真实 DWS CLI 和 main 身份服务复现了用户提供的完整提示，手动刷新仍失败。
- 同一夹具的 `auth status` 返回登录和令牌有效，但不会补回 profile 的 clientId。恢复完整元数据后，不退出登录也能初始化。
- 另一个损坏凭据夹具产生的是“DWS 身份查询失败”，与用户补充的提示不同，不作为本次修复根因。

旧错误把三个字段合并，缺少该用户原始 profile 输出，不能断言其实际缺失的一定是 clientId。可以确认的是：原实现没有区分字段缺失与登录失效，也没有提供准确的恢复指引。

DWS 上游参考：[固定提交的 auth status 实现](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/1b06d0105a27750a888a361abaa465f93b7f729d/internal/app/auth_command.go)、[profile 元数据实现](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/1b06d0105a27750a888a361abaa465f93b7f729d/internal/auth/profiles.go)。本次未修改 DWS 或宿主。

## 经确认的修复范围

1. 精确区分缺失或格式异常的 corpId、userId、clientId，提示不回显异常字段值或原始 CLI 错误。
2. 仅本人手动刷新，且唯一当前账号的组织、用户、实例主人、显式 profile 一致，只有 clientId 缺失时，针对规范的 `corpId:userId` 执行一次官方认证检查，然后重读一次 profile。
3. 认证返回必须明确成功，并匹配同一组织和用户、确认有效凭据。元数据完整后继续执行原绑定校验；账号变化、授权应用变化、模糊结果均不自动迁移。
4. 认证有效但仍缺少 clientId 时，说明“登录有效，但账号信息仍缺少授权应用 ID”，指引管理员在 Gateway 同一运行用户、目录和密钥环境对当前账号重新授权，再刷新；无需先退出所有账号。
5. 正常启动与正常刷新不增加认证查询；普通命令重试、自动启动不触发此检查。单次认证检查最多 15 秒，整轮仍受 30 秒预算和停止取消约束，不自动循环重试认证。
6. 不登录、登出、切换账号，不读令牌文件，不以机器人 clientId 或旧缓存填补缺失字段。不更改插件 ID、配置结构、状态路径、身份缓存 schema 或发送路径。

这是诊断与受控恢复入口修复，不承诺当前 DWS 能自动修复所有历史元数据。DWS 1.0.58 未补齐字段时仍需对当前账号重新授权；不能为了省略该步骤而绕过身份校验。
