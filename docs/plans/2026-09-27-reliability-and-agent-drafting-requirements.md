## 1. 已确认的要求与参数

- 保持一个源代码树，兼容 OpenClaw 2026.7.1-2 与 2026.8.1；插件 ID、原状态路径和既有持久化格式保持兼容。
- 起草默认不调用工具，新增工具能力须显式开启；新安装和旧版本升级均采用这一默认值。开启后只允许经核实、参数受限的无业务副作用工具；未知工具和写操作默认拒绝，不能弹出审批后在起草任务内放行。此项以用户最新确认的默认关闭为准，替代早先默认开启及沿用全部 Agent 权限的建议。
- 草稿最终发送继续由员工确认；消息发送由插件现有确认卡流程负责，不开放为起草 Agent 的工具能力。
- 历史消息提取接口返回的可用文字作为拟稿输入，不读取附件，默认回溯 5 分钟，可配置。私聊和群聊 @ 均支持；群历史只取本条 sender 与本人，不要求历史消息 @ 本人。
- 私聊同一人连续来信合并展示，最多显示最近 3 条。
- 卡片到期检查默认从 30 秒改为 10 秒，并允许配置；卡片有效期仍为 30 分钟，到期后后端立即拒绝过期操作。实施须同时拆开轻量到期检查与重数据清理，加入限速、退避和公平重试，已成功刷为过期的卡片不反复更新；不能只修改现有定时器间隔。
- 服务号过滤暂缓，不纳入本次开发与验收：目前尚未验证可靠的通用识别方法。撤销配套的“身份不明暂停自动发送”建议，不新增来源待核实状态或过滤配置；以后有可靠依据再另行评估。
- 卡片展示升级采用一个当前模板 ID；切换不兼容的新模板时停用旧卡，显示升级提示和打开新版助手入口，保留设置、规则、有效授权与可保留的草稿。普通 Pod 重启不因此作废当前版本有效卡片；不维护旧模板的完整业务页面。
- 正式开发须经过两版本地真机验证，每个大的修复、新需求独立本地 commit；GitHub 推送必须再经用户确认。
- 真机联系人：钟红发、阿童木；测试群：OpenClaw Test。执行时从当前 profile 的真实解析结果取得稳定 ID，实际 ID、配置、日志、截图和数据库不进入 Git 或发布包。
- Agent 由开发方选择；有工具起草推荐专用 `dws-draft` Agent，采用独立工作目录及严格查询工具允许清单。既有 `agentId` 仍服务于原无工具/分类路径；专用任务 Agent 通过新增 `assistant.drafting.agentId` 指定。正式实施前提供两版配置示例，评估阶段不修改用户运行配置。

用户已确认：固定正文与自动答复合并为“固定回复”，保留“逐条确认”和“条件内自动发送”两个选项，共用正文和规则编辑，消除独立入口的重复配置。该方向无需再次确认；开发已启动，验收进度另见执行记录。

### 1.1 已确认的默认参数与行为

用户先确认到期检查默认 10 秒及调度、重试优化，随后明确其余待定项均采用开发方建议。以下参数已确认，不再保留待答复状态：

| 项目 | 已确认值 | 对用户的实际影响 |
| --- | --- | --- |
| 卡片到期检查 | 默认 10 秒，可配置；与重清理拆分，失败更新限速、退避、公平重试 | 卡片有效期仍为 30 分钟；更快更新到期显示，后端按绝对有效期拒绝操作，成功更新后不反复刷卡 |
| 数据保留与重清理默认值 | 已处理正文保留 7 天、过期且完成界面处理的卡片保留 1 天、重清理 300 秒，均可配置 | 缩短数据保留，重清理间隔放宽到 5 分钟以减小扫描开销；有效卡、发送中/结果未知记录及待恢复状态仍受保护 |
| 连续私聊的定义与起草等待 | 相邻来信间隔不超过 30 秒、单批最长 5 分钟；安静 2 秒后起草，连续输入最多等待 10 秒 | 同一批最多展示最近 3 条；10 秒为起草前的合并等待上限，不是模型完成起草的时限 |

### 1.2 升级兼容的明确约束

- 保留插件 ID、状态路径、SQLite 既有表和业务键；本次主题逻辑简化不提升 `preferences.version` 或 `settings.version`，继续兼容当前 `version:1`。展示版本与业务数据版本分开。
- 保留 `topics.enabled`、`topics.mode=fallback/only`、规则 ID、条件、动作、正文、有效期、revision 和普通回复设置。缺少可选字段才补默认值，不把旧实例统一重置为默认设置，不重新开启监听或主题识别。
- 新的两分支策略适用于启用新逻辑后进入处理的新消息；原 `topic-review`、filtered 及待确认草稿保持可读，不批量重判或自动发送旧消息。仍可人工处理的旧草稿在新卡按当前版本和权限重新核对。
- 固定回复入口合并不把旧逐条确认规则升级为自动发送，不扩大或续期既有自动授权。发送结果未知的记录不自动重发，消息去重与冷却记录保持有效。
- 新安装和旧配置缺少 `assistant.drafting` / `toolsEnabled` 时均采用 `false`，保留明确保存的有效开关值；未启用工具无需先配置专用 Agent。有工具模式需要管理员在 OpenClaw 宿主配置中配置受限 Agent 和工具允许清单，不需要修改宿主源码，不由普通构建或测试偷偷更改运行配置。
- 数据兼容不等于无限保留：数据仍遵守对应有效期和经确认的清理策略。模板切换只撤销旧卡业务操作，不删除其关联的有效设置或草稿。
- 已有配置无法校验时保留原始数据并报告具体问题，不用初始化新设置掩盖错误。以脱敏的 0.8.0 配置和数据库夹具验证上述约束，再完成双版本真机升级验证。

| 项目 | 结论 | 证据与边界 |
| --- | --- | --- |

## 3. 本轮确认的现状与复现

### 3.1 存储

`assistant-store.mjs` 存放草稿、卡片、设置和通知覆盖信息。`source-store.mjs` 是兼容监听 Agent 的来源登记，容量 10,000，不能与助手草稿清理混为一谈。助手模式直接处理事件，不会每条都向 `sources.json` 新增登记。

现有行为：

- `assistant.sqlite`：WAL、`synchronous=FULL`；正文与元数据都在 JSON body 中。
- 维护定时器固定 30 秒，打开页面时也调用清理。
- 草稿有效期默认 24 小时，卡片交互有效期默认 30 分钟，导航不续期。
- 已发送、忽略、过期、替代、抑制、过滤的草稿保留 30 天；发送结果不明的记录不自动删除。
- 过期卡片保存 7 天，但另有总数 1,000 的硬裁剪，不区分是否仍有效。
- 本轮创建 1,001 张未过期卡片再清理，确认最早的一张有效卡被删除。这可能造成“界面可点、后端已无记录”。
- 删除行通常仅使 SQLite 页面可复用，并不等于数据库文件立即缩小；不能只看行数宣称磁盘已回收。

优化要求：缩短正文保留期，去重指纹与正文分离；清理分批、可配置，发送中/结果未知/有效交互卡片不得因容量上限误删；加入容量、清理结果和待恢复卡片数量等不含正文的诊断数据。

### 3.2 卡片过期

`maintenance()` 每轮按过期时间倒序取前 10 张待失效刷新卡片。模拟前 10 张持续失败，执行两轮：20 次请求只涉及同样的 10 张，第 11 张从未尝试。

还应覆盖：服务离线跨过有效期、重启、超过保留期、接口切换、在途正常页面更新晚于失效更新完成、平台超时但实际已更新，以及时间恰好等于有效期。现有测试已经检查服务端拒绝过期操作，但没有证明这些情况下手机最终一定显示过期。

验收：服务在线且平台可用时，到期后默认 15 秒内显示已过期并移除操作入口；失败有公平重试、退避和可诊断原因。平台持续不可用时不能保证外观及时刷新，但后端必须立即拒绝过期操作，恢复后补刷。

用户已确认默认每 10 秒执行轻量到期检查，并允许配置。该周期只缩短发现到期的等待，不改变卡片 30 分钟有效期；到期显示仍受任务调度、接口和客户端同步影响。验收同时核对检查与重清理独立、失败重试有预算、成功刷过期后不重复更新，以及到期检查期间按钮响应和正常卡片交互不受明显影响。

### 3.3 卡片卡住

当前 `handle()` 先持久化 `consumed=true`；`show()` 保存新卡片时，`store.card()` 会删除同一线上卡片的旧令牌，然后才请求平台更新。

隔离模拟连续更新失败的结果：旧令牌不存在，新令牌状态是 `deliveryState=pending`；用户再次点旧卡片没有任何额外更新请求。确认存在可复现缺陷，尚不能认定用户所有“无反应”都由此导致。

验收：操作立即得到处理中/完成/失败的可见反馈；平台更新失败后，可恢复同一张卡片并提供重新打开入口；重复点击不重复执行发送或设置操作；发送结果不明不自动重发；保护未提交表单内容。

### 3.4 主题与空草稿

本轮针对 `fallback` 模式做了三组隔离调用：

| 主题结果 | 最终状态 | 拟稿次数 | 空正文 |
| --- | --- | ---: | --- |
| 明确未命中 `none` | `pending` | 1 | 否 |
| 不确定 `ambiguous` | `topic-review` | 0 | 是 |
| 识别失败 `failed` | `topic-review` | 0 | 是 |

目前空正文通用占位会把“正在生成”“只整理”“需本人判断”“生成失败”等完全不同的状态都显示成“尚未生成”。该问题同时包含文案歧义与处理策略不符合用户预期；上表为现状记录，未来行为按已确认的 3.5 节变更。

普通处理实际选择 AI 时，未明确命中的消息应最终产生草稿或明确起草错误；用户实际现场若仍停在空正文，应结合阶段、队列、耗时及版本诊断继续定位。识别错误保留为运行异常；自动发送只能依据独立有效的既有规则授权，不能创造或扩大授权。

### 3.5 已确认的主题处理规则与四个边界

主题只有两个业务处理分支；分类原因、错误码可保留在内部和处理记录中，不形成“主题待本人判断”这一第三种待办。

| 处理结果 | 其他消息照常处理 | 只关注指定主题 |
| --- | --- | --- |
| 明确命中唯一主题 | 执行该规则设置的动作 | 执行该规则设置的动作 |
| 未明确命中 | 按当前对象的普通消息设置处理 | 不起草、不回复、不进入待处理列表、不触发逐条提醒 |

四个边界按用户确认执行：

1. 明确命中必须唯一、符合来源和规则条件、不涉及排除情形。使用固定模板时，模板须能完整回应整条消息。多主题同时匹配、部分覆盖、信息不足或无法判定都属于未明确命中，不随意选择某一主题。只整理规则没有模板正文，不附加模板完整性要求。
2. 只关注模式接受过滤实际相关但无法明确匹配的消息。保留受保留期约束、可在处理记录中查看的过滤原因，便于调整规则；不把它们放回待处理列表或逐条通知。不处理是业务动作，必要去重和最小诊断记录仍保留。
3. 其他消息照常处理完整沿用普通消息设置：AI 起草需确认、固定回复逐条确认或条件内自动发送、只整理、不处理。未明确命中包含主题冲突、无法判断和识别异常，不额外强制改为人工确认；普通消息的自动发送只有其自身对象、条件、授权期限和频率均满足时才能执行。设置摘要必须明确说明这一行为。
4. 识别接口故障、超时、无效返回也按未明确命中的业务分支处理，同时作为真实运行异常在助手首页/运行状态集中提示。显示受影响数量及时间，防止只关注模式下所有消息持续被过滤而用户不知情；不逐条创建待判断任务，不把故障伪装为模型明确判断无关。分类恢复后更新状态，不自动补发故障期间已跳过的消息。

主题明确命中后，仍由该规则的授权、频率和动作决定结果。授权到期、发送失败、发送结果未知、配置变更或任务过期不是“主题未明确命中”，不得借此回到其他自动规则重试。来源限制、暂停、不处理、只整理优先级和草稿版本校验继续有效。

界面文案使用“未明确命中的消息”解释两个选项；主状态展示真正动作，如“正在起草”“待确认”“仅整理”“已过滤”“起草失败”，移除空正文统一显示“尚未生成”。异常提示和过滤原因不进入回复正文。原 topic-review 记录保持可读，升级不自动追溯发送或批量重判历史记录。

验收：将唯一命中、明确无关、不确定、部分覆盖、多主题冲突、排除情形、格式无效、超时/调用失败分别放入两种模式测试；未明确命中在照常处理下完整覆盖普通回复方式，在只关注下全部无起草、无发送、无待办/逐条提醒且原因可查。校验故障集中提示及恢复、普通自动授权的期限/范围/频率、无规则场景、原有全局保护和历史记录不被自动重放。

## 4. 新需求

### N1：按指定 Agent 执行一次起草任务

新增 `assistant.drafting.toolsEnabled`，默认 `false`，即“无工具起草”。新安装、旧实例升级及字段缺省均走原无工具路径，不要求用户先配置专用 Agent。只有显式设为 `true` 才启用受限只读工具，并创建插件专属、与日常 Agent 会话隔离的任务。新增 `assistant.drafting.agentId` 选择有工具任务 Agent，未指定时继承顶层 `agentId`，但同样须通过只读权限检查；不能因未配置专用 Agent 而放行一个有任意写权限的 Agent。推荐使用专用 `dws-draft`，宿主层仅允许插件提供的受限查询工具，再叠加每次调用的执行校验。专用任务 Agent 的存在性和只读执行能力检查仅在工具开启时进行，不能让未启用的新功能阻断旧的无工具起草。

拆出这个配置是为了兼容性：现有顶层 `agentId` 同时被主题分类和无工具 completion 使用，非默认 Agent 的 completion 可能被宿主拒绝。不能把它直接改成新 Agent 而破坏原无工具路径。专用起草 Agent 可以使用与主 Agent 相同的模型和经选择的写作指引，但不共享其可写工作目录或全部工具。

关闭时沿用现有无工具 `llm.complete`，保留其宿主 Agent 选择权限边界；不把一次无工具调用失败自动改为有工具任务。无工具指模型不能发起工具调用，插件按 N2 配置预先取得近期历史作为输入仍可使用。主题分类始终使用无工具接口，不受此开关影响。

任务输入包含来信、受限历史上下文、员工写作要求及本次补充资料。仅提取任务的最终 assistant 正文，继续使用现有 160 字符限制；工具输出、推理、进度、审批描述不得成为代回复正文。无有效最终正文或超限时显示可修复错误。

“无业务副作用”定义为：起草工具不创建、修改、删除、移动或上传用户文件，不改变外部业务对象、权限、已读状态等，不发送消息/邮件，不建立日程/待办/审批/定时任务，也不能委派其他执行者间接完成这些操作。正常模型计费、查询服务访问日志，以及插件管理的必要会话/草稿状态不等同于工具获准修改用户数据；这些运行记录仍须有界并可清理。

允许能力以审核过的具体工具实现及参数为准，例如当前授权范围内的聊天历史、联系人、文档/知识库检索和内容读取。不是工具名含 read/search、声称 readOnly，或使用 HTTP GET 就自动安全。读取同样限定 profile、对象、目录/资源和返回大小，不允许借查询任意读取凭据或把私密原文发到未知地址。

起草任务禁用通用 shell/exec、任意脚本/Code Mode、浏览器与桌面交互、文件写入工具、通用网络请求、任意 SQL、跨会话转交和创建子 Agent 等绕行通道。需要 DWS 查询时，由插件提供固定子命令、固定参数形状的查询适配器，不让模型拼 shell。未知工具直接拒绝；需要写操作才能回答时，告知无法在起草阶段执行，可请求本人补充资料。

限制必须在真实工具执行前落实，并在受限适配器内部再次校验最终参数；提示词仅作说明。`deliver:false` 仍保留，但它只关闭最终答复自动投递。宿主/harness 若不能证明所有可达执行路径都受约束，则拒绝该有工具起草模式并明确提示，不能静默降级到不受限的 Agent。用户仍可选择 toolsEnabled=false 使用无工具模式。

任务结果须与草稿版本、批次、Agent、身份绑定。新消息、用户编辑、设置变更、过期或重启之后，旧任务结果不能覆盖最新草稿，也不能因超时或重启无界重复启动查询任务。

### N2：时间窗口内的对话文字

新增 `assistant.context.historyMinutes`，默认 `5`；建议允许 `0` 关闭，范围 0–60 分钟。

- 私聊：只取当前会话内对方与本人。
- 群聊：由当前 @ 来信触发，只取同群内本条 sender 与本人的发言；历史查询不传 `at-me` 过滤。
- 群内无法仅凭“本人发言”证明回复对象，所以这里承诺两个人的发言集合，不承诺精准识别每句一对一回复关系。
- 使用真实消息创建时间，限定输入快照截止时间，升序排列、按稳定消息 ID 去重；当前触发消息单独纳入，不重复。
- 2026-09-28 真机验证后经用户确认调整：提取接口返回的可用文字正文，不再要求源消息具有可靠纯文本类型标记。过滤明确的图片、语音、视频、文件、附件及卡片类型、资源字段、媒体占位和图片语法；不下载、解密或扩展读取附件，引用与合并转发也不扩展。类型缺失时允许文字投影，但不宣称能够区分已经被接口转成文字的卡片或富文本。
- 不扩大订阅范围为全群监听，不跨组织或会话取消息。
- 默认最多 50 条、累计 12,000 字符，超出明确标注截断。历史检索失败可用当前来信继续起草，并在卡片显示“历史上下文未完整取得”；不得无提示回退到跨天旧助手记录。
- 临时历史缓存仅在内存短期持有；持久化只留必要的消息 ID、窗口、完整性与来源元数据。Agent 会话产生的文本副本也纳入任务清理。

### N3：私聊连续来信最多 3 条

已确认定义：相同 profile、本人账号、私聊会话、sender，仍有未完成批次，相邻来信间隔不超过 30 秒，单批从首条起最长 5 分钟；检测到本人回复、完成发送、忽略或过期后结束当前批次。默认参数按第 1.1 节实施，不在开发时自行更改。

- 卡片按时间显示最近 3 条，每条显示时间；收到第 4 条后仅展示第 2–4 条，并注明还有较早来信。
- “卡片最多 3 条”与“历史输入最多 50 条”分别控制展示和拟稿，不为了展示限制而删除其他尚有去重或发送审计用途的记录。
- 新来信更新同一张活动通知卡并使旧草稿版本失效。拟稿以最新整批内容为输入，不只回复最后一句。
- 用短暂合并等待减少重复任务：已确认安静 2 秒后起草，连续来信最长等待 10 秒即建立快照。10 秒限制合并等待，不承诺模型在 10 秒内完成；已有通知频率、免打扰和手动查看设置继续有效。
- 用户正在修改时，保留输入并提示有新消息；不能覆盖表单或发送旧版本。
- 发送已取得执行权时冻结该批，新来信进入下一批；不能把新消息悄悄算入已批准的正文。
- 群消息不做此私聊聚合。修复现有同群不同 sender 互相替代草稿的行为，使群待处理记录按会话和 sender 隔离。

### N4：助手每个页面正文的系统性优化

覆盖既有 39 个页面以及空态、失败、过期、处理中、发送结果未知等变体，详见[独立设计方案](2026-09-27-card-content-design.md)。统一标题/状态、关键摘要、主体区块、必要提示、操作和脚注；规范字号、间距、强调、链接和状态语言。列表使用短摘要，发送确认完整显示接收对象和待发送正文；增加批量发送前的完整核对页，此流程调整随新设计方案获得确认。

新模板承载原生分区和受控富文本。只保留 `assistant.cardTemplateId` 用于新建卡片，不新增第二个模板 ID 配置。上线时先发布、预检新模板，再切换模板配置和展示版本；新模板未就绪不得提前停用旧卡或把新格式写入旧模板。取消旧版全部页面的纯文本兼容渲染器，旧模板仅用于既有卡片的停用提示与导航。

升级体验按用户最终确认执行：

- 旧卡停用原发送、保存、授权等操作，展示“助手已升级；这张卡片已停用。已保存的设置、草稿和待处理消息都已保留”，提供“打开新版助手”按钮和 `/dws` 备用入口。
- 点击后尽量回到同一条草稿、待处理列表或对应设置页，读取最新状态，不重新起草、不自动发送或重新授权。原记录已处理、过期、被替代或清理时说明真实状态；结果未知的发送仍要求核实。
- 若旧外观尚未刷新，点击旧发送按钮只导航到新卡并显示“助手已升级，本次点击未执行发送。请核对下方回复后重新确认”；不执行旧发送。旧保存、授权按钮也不执行原操作。重复点击合并，避免多张新卡。
- 普通 Pod 重启不天然让旧卡失效；状态目录持久化时卡片可恢复。本次仅在不兼容模板切换时迁移一次，普通重启和无关代码更新不重复停用当前卡。
- 保留设置、主题规则、有效授权、草稿、发送结果与去重信息，继续遵循相应有效期和清理策略。尚未提交的表单内容可能未到服务端，不能承诺恢复；明确提示可能需要重填，不把旧表单当成新的发送或授权批准。
- 停用权限先于外观刷新生效。平台故障恢复后补刷；旧卡仅保留通过本人身份校验的恢复导航，不能因兼容而恢复业务权限。新卡发送失败或结果未知时不跨后端盲目重发。

OpenClaw 两版均验证新模板完整业务页面及旧卡过渡体验，不再要求旧模板覆盖全部业务页面。不得把富文本标记写入实际待发送正文；禁止因展示升级重置用户设置或重复发送消息。

本项为已确认的验收目标。2026-09-28 已实现页面模型及升级流程，模板发布、实际可见卡片与回调验收尚未完成；不能将合成数据预览视为上线效果。

## 5. 固定正文与自动答复：已确认合并

下表只解释 0.8.0 的现状与区别，不代表新版本仍保留两个独立入口：

| 能力 | 正文来源 | 发送授权 | 当前适用范围 |
| --- | --- | --- | --- |
| AI 起草，我确认 | AI / 后续 Agent | 每条确认 | 默认、指定人、指定群 |
| 固定正文，我确认 | 员工预先填写 | 每条确认，可先修改 | 默认、指定人、指定群 |
| 自动答复 | 员工预先填写的固定模板 | 授权期内按规则发送 | 已监听范围、指定人/群、关键词或主题，受频率限制 |
| 只整理消息 | 不生成正文 | 不自动发送，可手动处理 | 同上回复方式范围 |
| 不处理 | 不入助手待处理 | 不发送 | 优先于其他回复方式 |

两者在预设正文部分高度重合，但发送授权时点不同。常用答复仍需要判断适用性时，逐条确认有价值；开会/休假等统一答复适合事先授权。已确认合并为一套固定回复功能，并保留这两种发送行为。

按用户已确认的方向合并为“固定回复”：共同编辑正文，选择“逐条确认”或“条件内自动发送”；后者再配置对象、关键词/主题、有效期和频率。AI 回复仍逐条确认，“只整理”和“不处理”保持独立含义。统一展示每条规则的正文、条件和发送方式，冲突明确提示，不能一处显示“我确认”，另一处却隐藏覆盖为自动发送。

此调整涉及规则归属与优先级，不能仅改文案后宣称解决。旧 `reply.fixed` 与 `autoRules` 不可无条件合并：正文、范围、条件和期限不同的规则仍要分别展示；已有自动授权不扩张，已有逐条确认规则不升级为自动发送。主题的多重匹配按 3.5 节视为未明确命中，进入普通处理或过滤，不能继续沿用“主题冲突一律转人工”的旧设计。进入普通处理后，其自身多个固定规则正文或发送方式冲突时不任意选择自动发送，可按普通回复的既有冲突处理规则转本人确认。界面必须在保存时预览受影响范围、自动发送授权和冲突。

## 6. 真机验收与交付边界

两版宿主逐项覆盖真实钉钉可见卡片及回调，不以 mock、历史报告、平台 HTTP 成功回执替代。联系人与群唯一解析后再测试，临时监听范围限于测试对象；测试前记录配置和状态，测试后恢复并核对。

每个大修复/新需求：相关自动测试通过、两版真机通过、恢复完成，才进行独立本地 commit。用户未确认推送前不执行 push。没有真机通过不得把开发任务标为完成；确有设备、授权或外部服务阻塞时明确报告所缺条件，不能伪造通过或把旧验收记为本次结果。
