# 助手卡片正文与信息设计优化方案

日期：2026-09-27。状态：用户已确认新设计及升级过渡方案，本文已按最终讨论更新；2026-09-28 已启动业务开发，模板发布和真机验证进度见[执行记录](2026-09-28-development-record.md)。本次提供页面审计、统一规范和交互评审稿；评审稿是合成数据的设计示意，不是钉钉真机截图或已上线效果。

关联：[总需求](2026-09-27-reliability-and-agent-drafting-requirements.md)、[实现与验收顺序](2026-09-27-reliability-and-agent-drafting-design.md)。本项覆盖助手的每个页面，不止首页或草稿页。

## 1. 现状与可行性

本轮检查了 assistant-views.mjs、assistant-config-views.mjs、assistant-topic-views.mjs，共识别 39 个页面名称，另有通知汇总、空内容、失败、过期、发送结果未知等状态变体。

当前模板以单个 BaseText 展示 description，最大 500 行；所有页面将状态、正文、说明拼进同一个字符串。show() 又把操作结果 notice 拼在正文最前方。正文没有可独立控制的分区、字体层级和提示区域；为 description 加 Markdown 标记仍会被旧模板当作普通文本。模板已有原生头部、表单、六个动作位和单独有效期脚注，可以保留这些交互约束并升级展示。

主要问题：

- 内容层级：运行状态、设置摘要、业务内容、错误原因和帮助说明同权重展示。
- 阅读顺序：长来信占满首屏，草稿与下一步动作被推后；记录列表展示过多正文。
- 语言：拟稿/起草、待回复/待处理等词汇混用；尚未生成无法解释实际状态；大量技术编号和 ID 影响阅读。
- 操作判断：完整发送正文、接收对象、授权期限的视觉重点不足，辅助说明却很长。
- 状态：保存成功、识别故障、发送未知、过期混在普通描述中，难以一眼判断是否需要行动。

结论：可以系统性优化。完整富文本效果需要配套升级钉钉卡片模板。最终采用业务数据兼容、新卡统一新排版、切换时主动停用旧卡并引导继续处理的方案；取消旧版全部页面的纯文本兼容渲染器，只保留旧卡停用提示和导航处理。

平台能力依据：本仓库导出的真实模板确认了原生标题、文本样式、间距、表单与动作组件；[钉钉官方卡片示例](https://github.com/open-dingtalk/dingtalk-card-examples)提供可导入模板及表单、循环渲染等示例；本轮已读取[官方新版 Markdown 变量文档](https://open.dingtalk.com/document/orgapp/markdown-variable-new)，确认其列出了标题、强调、段落、链接、引用、列表、分隔线等能力和原生字号/颜色 token。第一次浏览器打开在自动审批环节超时，重试已成功，当前不存在该阻塞。具体组件组合、长文本与表单共存、手机和桌面呈现仍需实施时真机验证，网页示意不能代替实际卡片结果。

## 2. 统一的信息结构

每页采用同一顺序，按需省略空分区，不填充装饰内容：

1. 标题与状态：说清这是什么页面、现在处于什么状态。标题不混入草稿版本和内部编号。
2. 关键摘要：最多 3–4 项当前决策所需的信息，如接收对象、处理方式、待处理数量、授权范围。
3. 主体内容：按独立区块展示来信、回复、规则正文、设置或试判结果。
4. 必要提示：只展示会影响下一步的异常、授权后果或变更；普通背景说明放帮助/详情。
5. 操作区和脚注：一项主要操作，其余按编辑/导航/撤销区分；卡片操作有效期保持独立，不与规则授权期限混淆。

正文只承担展示，表单继续使用原生表单；新增格式不能改变真实发送正文、授权或来源范围。正文区域也不能伪装成具有回调能力的按钮。

## 3. 排版、富文本与文案规范

| 项目 | 统一规则 |
| --- | --- |
| 视觉方向 | 简洁的钉钉原生工作卡片；蓝色仅用于主要操作和重点状态，避免满屏彩色、图标和 emoji |
| 文字层级 | 页面标题、分区标题、正文、辅助信息四层；采用平台样式 token，官方正文 token 对应桌面 14 / 手机 17，脚注为 12。评审稿仅表达层级，正式字号遵循客户端实际渲染与大字设置；正文正常字重，重点中等字重 |
| 间距 | 同组 4–8、分区 12–16、左右内边距约 16；以平台支持值和手机实测调整，不通过连续空格排版 |
| 主次区分 | 关键词/状态适度加粗；名称优先于 ID；时间和来源放次级行；关键错误与发送后果保持可读 |
| 分区 | 来信用中性引用区，回复用独立预览区；规则用标签—值排列；列表用分隔线或分组，不使用窄屏大表格 |
| 富文本 | 程序生成受控格式：加粗、短列表、段落、有效链接；标题、引用区、提示底色优先用原生组件。即使文档支持表格或部分 HTML，也不依赖窄屏大表格、任意 HTML 或未真机验证的折叠语法；评审稿中的展开详情可用原生详情页实现 |
| 换行 | 所有页面共用渲染规则：正文、操作提示和失效/升级指引使用段落，避免客户端两空格硬换行缩进；摘要、标题中的手工换行转换为空格，仍允许窄屏自然折行。表单原文和实际发送正文不改写。2026-09-28 已用同模板 A/B/C/D 真机对照确认；逐项结果见执行记录 |
| 内容长度 | 设置页开头 1–2 句；列表每条展示来源、状态及短摘要。原文截断须明确标记并可查看全文；发送确认正文不得省略、折叠或改写 |
| 颜色与无障碍 | 颜色始终伴随状态文字；适配浅色/深色及系统大字，次级文字仍可读；窄屏不横向滚动、不以缩字号解决拥挤 |
| 名称与编号 | 名称可换行，重名时补必要识别信息；普通页面隐藏内部版本和长 ID，详情/校验页仍能查完整 ID |
| 时间 | 明确使用用户设置时区；当日可显示 HH:mm，跨日显示日期。自动授权截止时间、消息时间、卡片有效期分别标注 |

统一措辞建议：面向员工使用“起草”“待确认”“待处理”“固定回复”“确认发送”“生成草稿”“重新起草”；首次从未生成使用生成草稿，失败时使用重试起草。只整理显示“已整理，按设置不生成回复”；没有待办显示“暂无待处理消息”；失败说明采用“发生了什么 + 可采取的动作”。

主题文案严格遵循已确认规则：明确命中唯一主题执行规则；未明确命中按普通方式处理或过滤。不能在新页面重新出现“识别不确定一律待本人判断”。工具默认无工具起草，不能在示例中暗示默认已开启工具。

## 4. 全部页面的改造清单

| 页面组 | 现有页面（39 个全部覆盖） | 正文改造重点 |
| --- | --- | --- |
| 首页 | home | 先显示当前状态与待处理数量；默认回复、自动授权和监听摘要分组；运行异常单独提示 |
| 监听范围 | listen、listen-dm、listen-at、listen-sender | 总览分私聊/群 @/额外发送者；子页只说明当前选择及影响；高级来源提示与普通说明分开 |
| 对象校验 | directory、search-results | 输入方法简短明确；结果按姓名/群名、识别 ID、结果逐项展示；失败具体到对象 |
| 回复方式 | reply、reply-target、reply-edit | 当前有效默认方式置顶；人员/群覆盖分区；正文/写作要求按所选方式解释；配合已确认的固定回复整合 |
| 主题策略 | topics、topic-mode | 展示主题开关、两分支处理摘要、规则数量；清楚说明普通自动授权仍可能生效 |
| 主题管理 | topic-manage、topic-detail | 每条规则展示名称、动作、范围、有效性；详情按匹配条件/排除条件/正文/授权分区 |
| 主题向导 | topic-new、topic-definition、topic-action、topic-trial、topic-limits、topic-review | 每步一个决策，固定步骤提示；试判突出实际动作和简短原因；最终确认完整展示对象、正文与授权 |
| 固定回复授权管理 | automation、auto-manage | 和固定回复合并后的入口保持一致；每条授权独立展示范围、正文摘要、截止时间和频率；旧规则可读，停用旧卡的回调仅引导打开新卡 |
| 固定回复授权向导 | auto-new、auto-content、auto-limits、auto-frequency、auto-review | 范围/正文/期限/频率分步短说明；最后使用授权摘要与完整正文，不把后果藏在长段落结尾 |
| 提醒设置 | notifications、notice-delivery、notice-frequency、notice-quiet、notice-priority | 总览为键值摘要；子页只展示本项作用与填写帮助；明确提醒关闭不等于停止已授权自动发送 |
| 待处理与历史 | inbox、history | 每页保持可扫读的少量记录；来源/状态/摘要分层，分页与选择一致；历史区分已发送、已过滤和待核实 |
| 回复处理 | draft、edit、regenerate | 对象与状态置顶，原消息和完整草稿分区；编辑说明不重复整段内容；起草要求与补充资料各自说明用途 |
| 暂停/恢复 | pause、pauses | 明确暂停对象与时间；恢复操作说明不重发旧消息；列表状态和空态清楚 |

这里的页面名 `topic-review` 是主题规则向导的最终核对页；旧草稿状态 `topic-review` 是历史遗留的主题待判断记录，两者不同。保留规则核对页不表示重新引入第三种主题处理分支；旧待判断记录只做可读和主动处理兼容，新消息不再创建此状态。

新增功能同样纳入规范：私聊最多三条消息按时间形成紧凑消息组；Agent 查询/起草进度展示当前动作和结果；主题故障在首页集中提示；旧版待处理记录使用兼容说明；清理/历史窗口等未来设置页使用相同设置布局。

动态状态必须逐类检视：加载/排队、起草中、无数据、内容过长、部分上下文、只读查询不可用、保存成功/失败、规则到期、发送中/成功/失败/未知、卡片过期、草稿被替代、升级停用与恢复入口。状态文案不能只改变颜色。

## 5. 关键页面交互

- 首页：先回答“助手是否正常、我有几条需要处理”，再展示监听、默认方式与自动授权。故障提示附影响和下一步，常态不显示长安全说明。
- 草稿详情：先明确回复给谁与待确认状态；原消息可分组并提供查看全文；完整回复单独展示。成功起草后确认发送为主要动作，修改和重新起草为次要动作，忽略与导航保持低强调。
- 待处理列表：每条只放识别对象所需信息和摘要，不重复长原文与完整草稿。原有批量发送必须在真正提交前完整展示所选对象和各条发送正文，确认绑定所选 ID/版本；摘要本身不能承担发送授权。这是小范围流程改动，需要独立验证，不能只更换按钮文案。
- 授权确认：依次展示对象/范围、条件、完整正文、期限、频率和发送后果。模板不得被富文本渲染改写后再存回业务正文。
- 主题详情：一页分“适用条件”“执行动作”“回复内容”“授权”；试判用“将执行……”解释实际路径，不向普通用户暴露枚举名。
- 空态/错误/过期：每种有明确原因和一个有效下一步。发送结果未知不提供盲目重发按钮；卡片到期提示重新打开，规则仍有效时明确二者独立。

## 6. 单一新模板与旧卡升级引导

### 6.1 已确认的取舍

引入共用的展示模型和新模板渲染器，页面输出标题、状态、摘要、正文区块、提示、脚注及动作语义，避免 39 个页面各自手写换行与 Markdown。切换新版卡片时主动停用旧卡，通过新卡继续处理；不再维护旧版全部页面与业务操作流程。

插件只保留现有 `assistant.cardTemplateId` 作为新建卡片的模板配置，不新增 `richCardTemplateId`，不要求管理员维护两个生效的模板 ID。钉钉后台保留旧模板供历史卡片显示及停用提示使用，不继续为其开发新样式；这不等于插件有两套业务页面。必要的历史模板元数据可由迁移过程内部保留。

仅安装插件不会自动替换钉钉云端模板。上线步骤应先发布、预检新模板，再切换唯一模板配置并启用对应展示版本；模板版本由发布流程明确登记，不能从任意模板 ID 猜测。新模板未就绪时不得提前停用旧卡、清除业务数据或向旧模板填写新格式。新模板就绪校验与切换步骤纳入部署文档及真机验收。

### 6.2 重启与升级的区别

当前卡片记录存于 SQLite；状态目录持久化时，普通 Pod 重启不会天然作废所有卡片。既有的到期、身份、接口切换、已消费按钮和草稿版本校验仍然有效。

本次因模板存在不兼容变化而进行一次明确切换。持久化展示版本及切换标记，切换时撤销旧卡业务操作权限，普通 Pod 重启或不涉及卡片兼容变化的代码更新不重复迁移、不重复停用当前版本的有效卡。切换不延长草稿或自动授权期限，不改变已保存的回复方式、主题规则和通知设置，不自动重放历史消息或重新起草。

### 6.3 用户看到的升级提示

旧卡移除确认发送、保存设置等原业务按钮，改为：

> **助手已升级**
>
> 这张卡片已停用。已保存的设置、草稿和待处理消息都已保留。
>
> 点击下方按钮继续处理。
>
> **【打开新版助手】**

脚注提供“也可发送 `/dws` 打开新版助手”。“已保留”指不因模板切换删除或重置；数据仍遵循原本适用的有效期与清理策略。升级不逐张推送替代新卡，用户点击入口时再打开对应任务，避免刷屏。

| 原卡片所在位置 | 新卡片落点 |
| --- | --- |
| 某条草稿详情 | 同一条草稿的当前版本，保留已保存回复，不重新起草 |
| 待处理列表 | 当前待处理列表 |
| 设置页或设置向导 | 对应设置页或其可用入口，展示已保存配置，不恢复未提交授权 |
| 已处理、已过期或已被替代的消息 | 说明当前状态，并提供返回待处理的入口；不得恢复旧发送权限 |
| 发送结果待核实 | 保留待核实状态和核对指引，不提供盲目重发 |
| 原记录已按保留策略清理 | 说明原记录已不可用，打开当前待处理列表或首页 |

新卡始终读取当前业务状态，不能把旧卡携带的正文、版本或表单值当作新的发送授权。员工不需要重新配置；已保存的草稿继续可见。旧卡输入框里尚未提交的内容，服务端未必收到，不能承诺恢复；编辑页切换提示应说明“尚未提交的修改可能需要重新填写”。同一版本卡片的普通刷新仍须保护未提交输入。

### 6.4 旧外观尚未刷新的点击与故障兜底

若升级停用提示尚未刷新，用户点了旧卡的确认发送、保存等按钮，先识别该卡已因升级停用：本次不发送回复、不保存旧表单、不创建或扩大授权，仅为通过身份校验的本人打开新卡。对于旧发送按钮，新卡显著提示：

> 助手已升级，本次点击未执行发送。请核对下方回复后重新确认。

其他旧操作使用“助手已升级，本次操作未执行。请在新版页面继续处理”。提示只说明本次点击，不能把之前已发生或结果未知的发送描述为从未发送。若消息已不可发送，应展示真实状态，不再要求确认发送。

旧卡恢复入口与旧业务动作分别授权，校验可信操作者、账号、来源卡片和持久化记录；未知或伪造回调不得打开他人的任务。旧业务按钮绝不因恢复导航而重新获权。过期的恢复入口提示使用 `/dws`，不能为了继续导航延长旧发送授权。重复点击合并为同一次恢复，避免重复创建新卡；发送新卡结果未知时不换 ID 或后端盲目重试。

先持久化撤销旧业务权限，再异步更新旧卡提示。平台暂不可用时，旧外观可能短暂保留，但后端仍拒绝旧业务操作；恢复后公平补刷。新卡也暂时无法打开时，给出可投递的失败提示及 `/dws` 备用入口，不承诺平台断线期间一定能显示反馈。过渡更新只使用原卡的既有后端，不把升级当成失败跨后端重发的理由。

### 6.5 实施与回退边界

- 新模板使用独立命名/版本的可导入模板，保留原生表单与六个动作位；先以三张能力验证卡核实段落/强调、引用与链接、长文本与表单共存，再锁定语法和组件。
- 保留旧卡最小记录用于停用提示、可信回调识别、导航落点和去重；在合理恢复期内不能直接删除后让用户点击无反馈，之后按既定清理策略回收。所有新页面仅使用新模板渲染器。
- 回调协议版本、展示版本与业务数据版本分别管理。旧数据缺少展示版本时按旧卡识别，不重置 settings 或草稿数据格式。
- 切换与卡片更新串行协调，旧的在途页面更新不能覆盖升级提示。切换前已经领取的业务操作按持久化操作记录核实完成或结果未知，不撤销已发送事实、不自动重放；新卡显示其当前结果。
- 不直接覆盖线上旧模板；保留旧模板供旧卡停用显示。现有平台导出包含 editorData 与编译后的 widgetInfo，升级必须由平台完成编译/导出并核对，不能只改本地 schema 就宣称线上可用。
- 回退必须同时核对代码、模板及数据兼容性，不能只改模板 ID、重新激活旧按钮或宣称旧插件必然识别新动作。恢复到旧版本须使用经验证的部署回退流程，不能为回退覆盖最新发送记录。

OpenClaw 宿主版本与卡片展示版本独立。2026.7.1-2 与 2026.8.1 均使用新模板完成全部业务页面验收；两版都需验证旧卡停用和导航引导，不再要求旧模板覆盖全部业务页面。

## 7. 内容正确性与防误操作

来信、姓名、模型草稿、固定正文均视为纯文本数据，由受控渲染器转义。不能让文本中的 HTML/Markdown、图片语法、@标记或变量表达式伪装系统状态、注入动作或自动加载外部资源。链接只允许经过校验的协议，展示目标域名，禁止 javascript/data/file 等链接；来信和拟发送正文中的原始链接文字仍可按字面完整展示。

展示格式不写回 d.text，不改变将发送的字符、顺序、链接或 160 字符限制。摘要截断按文字边界处理，不能截断 Emoji 或转义结构；详情始终可访问完整内容。提示内容与真正回复严格分离。

同一展示版本内，操作按钮改排保留原动作绑定，不复用索引导致旧按钮含义变化。正文折叠、详情切换和新消息刷新不能丢失未提交表单内容。模板切换时按第 6 节停用旧操作并提示未提交内容的恢复限制，不把旧发送回调改绑为新的发送动作。批量确认页需对全部选中项重新核对版本，变化时要求重新确认，不能只重画预览后沿用旧批准。

## 8. 验收与提交

1. 页面覆盖：为上述 39 个页面建立固定的合成输入与新模板渲染清单，覆盖已有数据/空态/长内容/错误；确认没有遗漏。新增和整合页补入清单；旧卡仅覆盖停用提示、导航和拒绝旧业务操作。
2. 真机矩阵：两个 OpenClaw 版本分别覆盖新模板完整页面及旧卡升级过渡；手机与桌面，至少手机常用宽度、窄屏、深色和大字；既有测试联系人和测试群按用户已授权范围执行。每页检查可见正文、控件和对应回调，不以网页版评审稿代替。
3. 内容矩阵：长中文姓名、重名、完整 ID、连续三条消息、长链接、Markdown 特殊字符、换行、Emoji、空数据、最大规则数量、到期与未知发送结果。
4. 可用性：首屏能判断状态、对象和主要动作；正文层级一致，无横向溢出、文字遮挡、意外图片或裸露标记。确认页完整正文可见；颜色之外有状态文字。
5. 业务数据兼容：旧设置、规则、有效授权和可保留的草稿不因切换丢失或重置，旧草稿可在新卡查看；过期、已处理和结果未知状态准确，切换不重复发送或自动重判历史消息，发送正文与新卡批准正文逐字相等。
6. 升级体验：旧卡出现已升级提示及打开按钮；草稿/列表/设置返回正确位置；未提交输入限制可见。提示刷新前点击旧发送按钮必须零发送并在新卡说明本次未发送；旧保存/授权按钮不执行写入。身份不符拒绝，重复点击合并，过期恢复入口使用 `/dws`。
7. 故障与重启：平台更新失败后权限仍已撤销、恢复可补刷；新卡创建失败或结果未知不跨后端重发；切换中重启能够接续，普通重启不重复停用当前版本卡片、不批量推送新卡。新模板未就绪不能提前执行停用切换。

建议在现有可靠性、主题及新能力完成后，按两个独立业务提交交付本项：

- 9a `feat: add structured cards and guided template upgrades`：共用展示模型、新模板渲染器、单一模板配置、旧卡停用与任务恢复导航，先在代表页面及全部升级过渡场景完成双版真机验证。
- 9b `feat: redesign assistant page content and confirmation layouts`：覆盖全部页面、统一文案、状态、列表及批量确认流程，完成完整矩阵与双版真机验证。

每个提交仍遵守先真机通过、恢复临时配置和状态、再本地 commit；推送另等用户确认。本轮仅准备设计文件和本地交互示意，不发布模板、不发钉钉消息、不改线上配置。

## 9. 确认状态

用户已同意“原生分区 + 有限富文本 + 简洁文案”的全页面设计，以及第 6 节的升级体验：保留业务数据，切换时停用旧卡并显示提示和打开入口，尽量回到对应任务；普通 Pod 重启不额外停用当前卡；旧发送按钮不得发送，重复点击合并，异常有补刷和命令入口，未提交输入可能需重填。

此前“双模板配置、双完整渲染器、旧卡保持全部功能直到自然到期”的建议不再采用。确认的是设计与升级策略，实际钉钉组件细节以能力验证卡和双版真机结果为准；本轮仅更新文档，未据此启动整体业务开发、发布模板、commit 或推送。
