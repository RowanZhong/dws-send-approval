# 可靠性优化与 Agent 起草：实现、验收及提交方案

## 1. 实现边界

保持插件 ID `dws-send-approval`、现有状态目录、旧配置键、旧草稿和卡片可读。新增配置带默认值；数据库以新增表、索引和可选 JSON 字段扩展，不重命名、删除既有字段。老数据按单消息草稿解释；原 `sources.json` 的来源保护继续有效。

旧卡可读用于识别来源、停用提示和恢复导航，不承诺不兼容模板切换后仍可执行旧业务操作。业务数据保持兼容，所有新业务页面统一使用新模板。普通 Pod 重启不触发卡片展示迁移。

仍由 `card-transport.mjs` 选择新版公共接口或旧版桥接。不得把失败的发送转到另一后端重试。现有 channel 仓库及员工运行配置不作为构建或测试的副作用修改。

用户已于 2026-09-28 正式启动开发，分支为 `codex/reliability-agent-drafting`。各大项必要真机验证通过后独立本地提交；未经另行确认不推送。本文末尾的早期讨论记录保留当时的文档阶段状态，当前实施及验收状态见执行记录。

## 2. 配置建议

下表含已有字段和本分支新增字段；已加入开发版运行时 schema，不能将整表直接复制到已发布的 0.8.0 实例。工具默认关闭、历史默认 5 分钟、到期检查默认 10 秒以及需求第 1.1 节的数据保留/重清理和私聊批次参数均已确认；其他标为建议的技术范围与预算仍按需求边界通过测试校准。服务号过滤已暂缓，不新增相关配置或身份不明时暂停自动发送的策略。

| 字段 | 默认值（确认状态见说明） | 说明 |
| --- | --- | --- |
| `agentId`（已有） | `main` | 保留原分类、无工具起草及兼容监听含义，仍受宿主 completion 选 Agent 的授权约束 |
| `assistant.cardTemplateId`（已有） | 保留现有字段 | 唯一的新建卡片模板 ID；部署时先预检新模板再切换，展示版本由升级流程登记，不新增第二个模板 ID 配置 |
| `assistant.drafting.agentId` | 继承 `agentId` | 有工具任务 Agent，必须通过只读权限检查；部署建议明确设为专用 `dws-draft`，不能自动用不受限的 main 兜底 |
| `assistant.drafting.toolsEnabled` | `false` | 新安装及升级缺省均沿用无工具 completion；显式开启后才运行带受限只读工具的 Agent 任务 |
| `assistant.drafting.timeoutSeconds` | `120` | 本轮等候预算，10–600；超时不视为宿主已取消任务 |
| `assistant.context.historyMinutes` | `5` | 0–60，0 关闭历史检索；不影响当前批次原文 |
| `assistant.storage.retentionDays` | `7` | 默认 7 天且可配置已确认；已处理消息正文保留期，范围建议 1–30 天；旧值固定 30 天 |
| `assistant.storage.expiredCardRetentionHours` | `24` | 默认 1 天且可配置已确认；过期且完成界面处理的卡片保留期，范围建议 1–168 小时；旧值固定 7 天 |
| `assistant.storage.cleanupIntervalSeconds` | `300` | 默认 5 分钟且可配置已确认；重数据清理间隔，范围建议 30–86400 秒 |
| `assistant.storage.dedupeRetentionDays` | `30` | 不含正文的去重指纹保留期，须不短于正文保留期 |
| `assistant.cards.expiryCheckSeconds` | `10` | 默认 10 秒及可配置已确认；与重清理独立运行，配置范围建议 5–60 秒；旧维护周期 30 秒 |
| `assistant.directBatch.mergeGapSeconds` | `30` | 默认 30 秒已确认；私聊相邻消息合并间隔，配置范围建议 1–300 秒；最多显示 3 条固定为产品规则 |

减少存储主要靠缩短正文保留期，而不是更频繁扫描整库。到期检查 30 秒变 10 秒、与重清理拆分以及失败重试优化已获用户确认；正文 30 天变 7 天、过期卡 7 天变 1 天、重清理扫描放宽到 5 分钟也已确认。拆分旨在减少同步 SQLite 工作对交互的影响，实际效果须验证。历史窗口、草稿 TTL、卡片 TTL 仍是独立概念，原草稿 24 小时/卡片 30 分钟暂不改动。

用户已确认 `toolsEnabled` 默认关闭，新安装和旧版本升级采用相同策略。缺少整个 drafting 对象或 toolsEnabled 字段时都补为 false，不要求旧实例改宿主配置或新增专用 Agent，既有显式布尔值原样保留。工具关闭时不执行专用任务 Agent 的存在性/只读能力预检；显式开启后才检查，无法确认隔离有效则拒绝该有工具任务并说明原因，不能扩大权限或隐式切换路径继续。此开关不关闭插件按历史配置预先读取消息，也不改变主题分类的无工具实现。保留期缩短会清理超过新保留期的已处理正文，部署前按正式运维流程备份，不能在单元测试中触碰真实状态。

开启受限工具需要配置 OpenClaw 宿主中的专用/合格 Agent 与工具允许清单；只改插件里的开关不足以建立只读边界。不修改宿主源码，不修改日常 Agent 的全局权限；配置示例按两版实际 schema 分别提供，开发真机使用临时配置并在每次验收后恢复。

## 3. 数据、清理与磁盘

修改 `assistant-store.mjs`，拆开 `expireDrafts`、`pruneTerminalRecords`、`pruneCards` 等职责。

1. 增量加入纯指纹表，保存 profile/会话/消息派生键、首次见到时间和终态；删除正文前在同一事务保留指纹。现有消息键不改，旧记录逐批回填。
2. 收到明显早于允许重放窗口的事件不能因为正文已清理而再次发送；以验证过的消息时间和指纹共同控制，时间异常不作自动发送依据。
3. 草稿业务过期、卡片交互过期和数据物理清理分别处理。`sending`、`unknown`、宿主未终结的 Agent run 不自动清除；显示诊断供核实。
4. 删除终态正文以明确的完成/过期时间为准，兼容旧行只含 `updated` 的情况；不能在刚转过期时立即把需要展示和诊断的记录按旧更新时间删除。
5. 删除卡片先检查交互有效性、待更新任务、未完成操作和引用；取消“最新 1,000 条以外全部删”的规则。压力达到阈值时合并通知或限制新建，不能无声删除有效卡。
6. 待补刷的过期卡片只保留恢复所需的最小数据，不为一张永远失败的卡永久保存来信正文。公平重试有期限，到期记录补刷失败的计数和原因，不冒充刷成功。
7. 清理配套清除无引用的通知覆盖、目录失效缓存、冷却记录和已结束任务元数据，但不得删尚未核实的旧监听来源登记。
8. 清理分批并使用索引，避免每次点按钮同步扫描/整理整库。记录 DB/WAL 字节数、行数、可复用页数和最近清理结果。

磁盘回收：WAL 做空闲期、有超时的 checkpoint；删除后的主库页面优先复用。既有库默认没有 incremental vacuum，不能加一条 pragma 就承诺缩小。若压测发现主库空闲页过多，设计独立、互斥且可失败重试的空闲整理阶段；先验证锁等待和额外磁盘空间，再决定是否默认自动执行。交互热路径禁止 `VACUUM`。验收分别报告删除数据量、可复用空间和实际磁盘变化。

## 4. 卡片状态机与恢复

### 4.1 过期刷新

独立调度卡片有效期检查，默认 10 秒且可配置，已获用户确认；每轮按索引有界领取到期任务，不连带执行整库清理，也不改变通知调度频率。持久化 `nextAttemptAt`、尝试次数、错误类别等可选元数据；按到期及下次尝试时间公平领取任务，不再固定取同样的前 10 张。每次更新有请求预算、限速和退避，已成功显示过期的卡片不重复更新。不能只将现有维护定时器的 30000 改成 10000。

双版验收记录到期显示延迟、更新次数和按钮响应；核对正常卡片不被周期性重刷、成功失效更新不重复、平台故障不会导致每 10 秒无节制重试。卡片有效期仍为 30 分钟，点击时按绝对到期时间检查，不等待下一轮维护；检查频率不构成额外可用宽限期。

每个 `outTrackId` 串行更新；执行前后核对卡片版本、有效期和接口。过期后的普通页面更新不得覆盖已过期外观。服务启动先建立失效补刷任务，再执行物理清理；平台恢复后继续未完成任务。

### 4.2 按钮执行与界面投递解耦

保留旧令牌到有效期/恢复期结束，另存当前线上卡片指针和更新任务；不能在平台确认更新前丢失旧按钮的查找能力。

- 动作有持久化的 operation ID、已领取/执行中/完成/失败状态。领取在事务内完成，重复回调读同一结果，不重新发送。
- 导航/表单显示是可恢复更新；已执行的业务动作与是否刷卡成功分别记录。
- 卡片更新失败只重试同后端、同 `outTrackId` 的显示更新，不重试消息发送。结果不明的首次新卡发送也不换新 ID/后端盲目重发。
- 同一展示版本的旧令牌被点时可刷回当前页面或提示已完成/已失效；身份校验、绝对有效期和草稿版本校验保持不变。已因模板切换停用的旧卡只走 4.3 节的恢复导航，不恢复旧业务动作。
- 首次点击尽快返回 Stream ACK，同时后台显示处理中；目录查询、Agent 等候、DWS 请求不阻塞回调 ACK。
- 表单字段保留原版本命名空间；收到新消息不能覆盖尚未提交的输入。
- `/dws`、`/dws show` 等文字入口继续可用，卡片失败给出明确恢复指引和不含正文的错误码。

自动化覆盖持续/瞬时更新失败、更新结果未知、进程重启、重复点击、过期与更新乱序、设置版本冲突，以及“发送成功但刷新失败不得再发”。两种 transport 都运行相同契约测试。

### 4.3 已确认的模板升级与旧卡引导

采用单一当前模板配置、新模板完整页面渲染和旧卡最小引导处理。取消两种完整页面渲染器及 `richCardTemplateId` 建议。完整提示文案和页面落点见[卡片正文方案第 6 节](2026-09-27-card-content-design.md#6-单一新模板与旧卡升级引导)。

1. 上线前先发布、编译导出并预检新模板，然后切换 `assistant.cardTemplateId`。明确登记展示版本与切换标记，不能由 Pod 启动次数、插件版本变化或任意模板 ID 推断应当停用全部卡片。新模板未就绪不执行停用切换，部署流程报告尚未完成升级。
2. 在现有持久化格式中增加可选展示版本及切换恢复元数据。缺少展示版本的老记录识别为旧卡，保留其 owner/account/track、页面与草稿引用，以及恢复去重所需信息。普通重启恢复同一迁移进度，不生成新一轮停用或批量推送。
3. 撤销旧卡业务权限与登记迁移进度在事务内完成，再将旧卡显示更新加入公平重试队列。先撤权后刷提示，更新失败不影响后端拒绝旧动作；旧的在途页面更新不得覆盖升级提示。已领取的发送动作按既有操作日志核实结果，不因切换取消已发生事实或自动重发。
4. 用旧模板原有字段显示“助手已升级”、保留数据的说明、“打开新版助手”按钮和 `/dws` 备用入口。现有旧模板按展示状态控制表单可见性，不能直接复用隐藏全部控件的 expired 外观而把恢复按钮一并隐藏；服务端业务停用标记与界面导航可点击状态分别管理。只实现这张停用提示，不再渲染旧版 39 个页面；旧模板保留在平台，插件不维护第二个生效模板配置。旧通道是否需要历史模板元数据须按其实际更新契约核对，不让用户手动维护双配置。
5. 回调入口先校验可信操作者、账号、来源卡片和持久化记录，再区分当前卡业务动作与已迁移旧卡的恢复导航。旧发送、保存、授权回调不得执行原动作或采用旧表单内容；导航到新卡后读取当前草稿/设置，旧发送点击明确提示“本次点击未执行发送”。若已有发送结果未知，保留待核实状态，不能宣称此前未发送。
6. 恢复导航有独立、限时的令牌和持久化去重记录。同一旧卡重复点击复用同一次恢复操作，不生成多张新卡；创建结果未知时不换 ID/后端重发。超过恢复期或原记录不可用时给出当前状态和 `/dws` 指引，不延长旧业务授权。不能识别或身份不符的回调拒绝导航。
7. 新卡落点按原任务映射：同一草稿的当前版本、当前待处理列表、对应设置页或可用入口。过期/已处理/被替代/清理的记录明确说明，结果未知的发送仍要求核实。已保存设置、草稿、授权与去重信息保持，不重放历史消息或自动起草；尚未提交的输入可能需重填，不能当成已保存数据。

迁移完成后，仅新模板承载业务页面。只有新的不兼容切换才会触发后续迁移，普通 Pod 重启不额外作废当前有效卡。回退须验证代码、模板和数据的一致性，不能通过改模板 ID 或删除切换标记重新激活旧业务按钮。

双版验收覆盖：新卡全流程；旧卡升级提示和按钮；草稿/列表/设置落点；提示未刷新时旧发送零发送、旧保存/授权零执行；重复点击仅一次恢复；错误身份拒绝；未提交输入提示；旧消息过期/已处理/发送未知；平台失败补刷；新卡投递结果未知不重发；迁移中重启接续；普通重启保持当前卡有效；新模板未就绪不提前停用。以可见卡片及实际回调验证，不以读取源码或现有重启单测代替。

## 5. 已确认的主题两分支处理与回复方式

本节按用户最终确认更新，替代早先将不确定/失败留在主题待判断的方案。本分支已按此设计实现，发布前仍须完成执行记录中的真机验收。

### 5.1 主题决策与普通处理

新增统一的主题处理决策：明确命中唯一适用规则则执行该规则；其余均为未明确命中，`fallback` 进入普通消息处理，`only` 过滤。保留 `topics.mode=fallback/only` 及旧配置键，不给用户新增第三种主题处理状态。

- 在模型输出和执行异常之上建立业务决策层，可继续读取旧 `match/none/review` 结构。业务决策只产生命中/未明确命中；原判断、reasonCode 和运行异常单独保留，不能把超时改写成模型明确判断无关。
- 明确命中须唯一且满足完整条件，模板完整覆盖、来源和排除条件均校验。多个候选同时匹配即未明确命中；不确定、部分覆盖、排除情形、无效返回、识别失败/超时均走相同的模式分支。只整理规则按其条件匹配，不要求不存在的模板正文能覆盖消息。
- `only` 的所有未明确命中统一落为 filtered，保留可查原因和去重信息，不创建待办、起草任务或逐条通知。没有适用/启用主题也走此分支；若只关注模式下完全没有启用规则，在设置和首页明确提示所有消息都将被过滤。
- `fallback` 调用共享普通处理入口，使用当前对象的有效回复方式，避免在多个分支复制 AI/固定/整理逻辑。保留普通固定回复的有效自动授权：主题不确定和识别异常不会新增 manualOnly 限制，不能把用户选择的普通自动回复暗改为逐条确认。普通规则自身的范围、条件、期限、频率、冲突及发送去重仍必须通过。
- 先执行身份、监听来源、全局暂停、会话暂停、不处理等原有入口限制，保留只整理的优先约束。配置变更、关闭、草稿过期或被新消息替代继续使旧任务失效，不能当作识别失败借回退绕过 valid/version 检查。
- 唯一主题命中后发生的授权过期、频率抑制、发送失败或结果未知，属于该规则的执行结果。沿用对应确认/抑制/待核实行为，不能改走普通自动规则或另一后端重试发送。普通自动规则自身冲突属于普通回复的处理问题，与“多个主题匹配”的回退含义区分。

分类失败后，fallback 按普通设置尝试处理一次，不循环重跑分类。普通模式为 AI 时，如共享模型故障使起草也失败，显示正常起草错误及重试入口；不能因分类失败无限排队。重启或升级不自动重放历史 topic-review/filtered 记录，保留旧状态可读和主动处理入口，不追溯触发自动发送。

### 5.2 界面与运行异常

在 `assistant-views.mjs` 建立统一状态文案，列表与详情复用真实动作：正在识别/起草、正在查询资料、待确认、仅整理、已过滤、起草失败、已被替代、已过期、发送待核实。正文为空不能统一显示“尚未生成”。正常回退后的主状态由普通处理决定，不能继续显示主题待本人判断。起草阶段的写工具直接拒绝，不提供批准后写入的入口。

选项说明改为“未明确命中的消息”：其他消息照常处理 / 只关注指定主题。普通自动发送可能在不确定、冲突或识别异常的回退中生效，这一点必须与有效对象、正文、授权期限一起出现在设置摘要中。只关注模式说明可能过滤实际相关但无法唯一匹配的消息，并提供处理记录入口查看原因。

分类接口失败、超时、无效返回和队列不可用集中计入运行健康状态。首页展示“主题识别异常”及最近时间、受影响数量、简短原因，保留最近成功时间以便判断是否恢复；提示必须基于实际分类能力，不能因无适用规则而跳过分类、普通处理成功或起草成功就宣称分类恢复。后续实际调用成功并返回有效分类结果时恢复状态，包括有效的明确未命中结果。提示与业务两分支独立，不产生逐条主题待办，不自动补处理或补发故障期间跳过的消息。

记录 phase、queuedAt、startedAt、finishedAt、reasonCode、实际处理分支及规则来源，区分过滤、普通处理、分类故障和起草错误；内容受保留期及容量约束，不保存原始工具响应或多余正文。诊断提示、过滤原因与发送正文分离。

### 5.3 固定回复兼容及验收

用户已确认合并固定正文/自动答复：共用“固定回复”入口与正文编辑，在规则内部选择逐条确认或条件内自动发送，统一展示范围、条件和期限。继续读取原 `reply.fixed`、`autoRules` 和主题模板，呈现为带来源的规则，只有语义相同的规则才合并显示。

保存自动发送选项仍经过授权摘要，旧逐条确认规则不静默升级；范围扩张或正文变更不得不经提示继承旧授权。主题冲突遵循 5.1 节进入普通处理/过滤；普通固定规则自身冲突不任意选一个自动发送。主题处理可先适配现有普通规则独立提交，固定入口合并随后独立提交。

新增测试矩阵覆盖：唯一完整命中、明确无关、不确定、部分覆盖、多主题匹配、排除情形、无效返回、超时、调用失败和队列繁忙 × 两种主题模式。fallback 再覆盖 AI/固定确认/有效自动回复/仅整理/不处理，only 确认所有未明确命中都无起草、无发送、无待办和逐条提醒且过滤原因可查。校验故障集中提示及真实恢复、无启用规则、自动授权期限/范围/频率、普通规则冲突、主题执行失败不再回退、版本失效、重复事件及旧记录不自动重放。两版真机分别核对实际卡片、过滤记录、运行提示与回调。

## 7. 历史上下文适配器

新增 `assistant-context.mjs`，DWS 执行继续复用 `assistant-dws.mjs` 的有界进程调用。

优先使用按确定会话读取的 `+chat-messages`，传准确 `[start,end)` 窗口、分页/条数上限且不下载资源，不使用全局扫描去补未知会话。拿到消息后在插件内再次验证会话、时间、类型和发送者。`+search-msg` 虽有 sender/time 过滤，但显式会话可能内部执行有界全局扫描，不作为默认历史路径。

本人身份从既有 identity discovery 取得 open ID，与 ownerUserId 区分；必要时将经核实的本人两种 ID 映射为同一个参与者。无法建立稳定映射时报告上下文不完整，不能按显示名匹配。

结果提供 `messages`、窗口、`complete/partial/truncated`、失败类别。按 2026-09-28 用户确认，接口返回的可用文字进入 prompt，缺少源类型不再整体拒绝。过滤明确媒体/卡片类型、媒体占位、图片语法和资源字段；引用、合并转发、资源字段不扩展读取，不下载附件。记录文字条数、过滤数量及 `textProjection/attachmentsRead:false`，不保证识别被接口拍平成普通文字的卡片。当前批次消息与历史按消息 ID 合并，优先使用已校验事件内容。时间边界采用实际消息创建时间，延迟事件或在途新消息不能污染已建立快照。

短期内存缓存按 profile/account/conversation 及窗口区分，最长 30 秒、容量受限；新来信合并补齐，发送者过滤在每次构建 prompt 时重做。重启后重新读取，不把群历史写成长期聊天档案。

测试：5 分钟边界、0 关闭、非文本排除、本人手动发言、群内未 @ 的 sender 发言、其他成员排除、时间乱序、分页部分失败、跨账号同 ID、重复触发消息、Agent 输入里没有窗口外文本。

## 8. 私聊批次与并发

新增 `assistant-batches.mjs`，批次键至少包含 profile/account/conversation/sender；每批维护单调递增 revision、消息成员、当前草稿 ID、当前卡片 track、开始与最后接收时间。

已确认的默认行为：相邻来信间隔不超过 30 秒、单批从首条起最长 5 分钟；安静 2 秒后建立快照开始起草，连续来信最多合并等待 10 秒，不被每条新消息无限重置。10 秒不是模型运行超时；已在运行的任务仍遵守下述串行和版本约束，不为满足等待上限而无界并发。本人回复、完成发送、忽略或过期结束当前批次。

聚合先于主题判定和 Agent 起草：多条连发组成一个问题整体后再判断主题覆盖，避免只按最后一句自动套固定模板。已开始的旧分类/拟稿结果按版本丢弃；为限制重复查询和模型成本，有工具任务不因新消息自动无界并发重跑，需跟踪前次终结后再处理最新快照。

最近 3 条仅是卡片展示上限。批次消息 ID 与必要原文按现有保留期管理，不能为省展示空间删除去重信息。卡片过期后旧卡失效，后续通知按新卡规则处理，不能借新来信无限续旧卡寿命。

群里两个 sender 独立保留待处理草稿，避免当前仅按 conversation 替代造成交叉丢失。本人回复若来自插件，通过发送成功记录即时结束批次；外部手动回复通过有界历史读取确认，不能依赖被 DWS self-loop 过滤掉的入站事件。确认时如发现本人已在手机回复，应提示重新核对而不默默代发旧草稿。

验收覆盖相邻间隔 30 秒及其两侧、单批 5 分钟上限、安静 2 秒触发、连续来信达到 10 秒仍建立快照、最多展示最近 3 条，以及起草中继续来信时的版本隔离与有界排队。两版真机使用已确认默认参数验证实际体验，自动化另覆盖可配置值和时间边界。

## 9. Agent 起草适配器

新增 `assistant-draft-runtime.mjs`，保留 `assistant-model.mjs` 作为默认无工具实现。入口按已归一化的 toolsEnabled 选择，仅 true 启用受限 Agent 任务，不做隐式失败降级。新增验收覆盖新安装缺省、旧配置缺少 drafting/开关、显式 false 和显式 true；前三者无需专用 Agent 即可走原起草接口，显式 true 才执行只读预检，重启/升级不改变已保存的选择。

流程：校验当前 Agent、实例身份和只读执行能力 → 保存 draft/version/batch 与独立 sessionKey 的映射及只读策略版本 → 启动受限宿主任务 → 保存 runId → 分段等待 → 读取最终 assistant 正文 → 校验当前版本与状态 → 写入待确认草稿 → 刷新通知 → 在安全终态清理专属任务会话。

- 会话使用插件专属标识并路由到配置的 Agent；幂等键绑定草稿版本。与原 `:dws-listener:` 发送审批会话明确区分，不能让旧策略把新起草任务当成未知来源或普通主会话。
- 使用两版共同支持的 `sessionKey/message/extraSystemPrompt/lane/deliver/idempotencyKey`；不假设旧版有 `disableTools` 或 `promptMode`。工具关闭走 completion，不向旧版传不存在的禁用字段。
- 新版返回 canonical sessionKey 时校验并持久化；旧版仅返回 runId 时保留请求会话键并做读取验证。
- 采用目标 Agent 的模型与写作上下文，不额外传 provider/model 覆盖。有效工具权限是宿主/Agent 已有权限与起草只读策略的交集；插件不能扩权。没有 Agent、只读隔离不可用或宿主拒绝调用时明确报错，不切换 Agent。
- 使用专属 lane，限制本地排队和并发，不占主会话唯一执行槽；工具查询等待时卡片导航仍可用。
- 新版 `pending` 是未终结状态，不能当失败；`timeout` 只是一次等候超时。超预算后卡片说明任务未确认结束，停止复用其输出；仍跟踪 run，不能声称已取消或马上重启同一工具任务。
- 如两版公共接口没有统一的可靠取消能力，不导入私有宿主文件实施取消，也不靠删除会话冒充取消。旧任务未终结时避免重复启动同一查询任务，允许人工编辑回复；保留只读约束直到旧任务真正结束。
- 只读最终 assistant 文本；剔除 tool/reasoning/progress。空输出、工具调用中断、超限、读取失败各自有明确状态。
- 持久化任务表仅记录本插件任务；重启后对账 run，不重放工具操作。会话清理调用公共 deleteSession，仅处理已终结且属于本插件的会话；清理失败可重试并受容量监控。
- 起草中的写操作、消息发送、未知工具一律阻断，不以宿主审批代替只读约束。最终代回复由确认卡调用插件发送流程；该明确授权的发送不属于 Agent 起草工具。

### 9.1 只读工具实现与启用条件

两版有 `before_tool_call` 执行前阻断，但 `subagent.run` 没有共同的任意逐次只读工具清单参数；新版 `toolsAlsoAllow` 是追加能力，不能误作缩小工具集。推荐以专用 Agent 的宿主工具允许清单、插件专属会话执行拦截和固定查询适配器三层限制共同实现。不能只依赖一个 hook 阻止原本任意可写的 Agent。

1. 建立维护在代码中的审核清单，绑定具体工具来源、实现契约和允许参数；不能靠模型判断，不能只相信 `readOnlyHint`、工具名、HTTP 方法或第三方描述。首批优先覆盖受限的联系人、历史消息、文档/知识库检索与读取。无法核实的工具不加入；后续扩展必须补执行测试。
2. 专属会话建立前就安装约束，校验 session/agent/run 与持久化登记。已保留的起草会话即使重启、超时、配置关闭、热重载也继续受保护；身份缺失或冲突不能当成普通会话放行。普通用户 Agent 会话不改变权限。
3. 每次调用检查工具及最终参数。固定查询适配器的 execute 内再次校验 profile、资源范围、数量和输出上限，防止其他 hook 改参或工具同名混淆；工具注册冲突、缺少校验上下文则拒绝。
4. 通用 `exec`/shell、脚本解释器/Code Mode、任意 HTTP/SQL、浏览器/桌面操作、写文件、发送、跨会话转交、子 Agent、定时任务等均不在允许清单。工具检索/动态加载不能绕过限制，新发现工具默认不可执行。
5. DWS 读取由插件在适配器中选择已核实的只读 leaf，以 `spawn(..., {shell:false})` 传固定 argv；模型只提供经过 schema 校验的查询条件，不提供可执行程序、子命令、环境变量、下载/导出路径或 shell 文本。查询不得附带自动下载、保存到任意文件或标记已读等操作。
6. 两版分别核实实际 Agent harness、原生工具、MCP/插件工具与工具策略及 hook 链的覆盖。目标 Agent 的有效工具集必须仅包含经审核工具；专用 Agent 限制必须作用于实际模型工具面，不是仅检查配置文件写了某个 allow 数组。若存在绕开宿主工具限制的原生执行路径，必须选受支持的运行方式，否则拒绝有工具起草；不能修改日常 Agent 的全局权限来凑测试。
7. 同时检查宿主插件是否在 Agent 生命周期中自行写入用户记忆文件/业务数据。这类行为可能不经过工具 hook；无法对本次会话禁用或隔离时，不宣称无副作用，也不启用有工具起草。受控会话日志、缓存与草稿保存仍归插件正常持久化管理。
8. 资料不够或只读工具不可用时，说明缺口，允许手动补充或显式关闭工具；不为了完成起草临时扩大权限。查询本身还受数据范围限制，禁止把私密资料随任意外部 URL/查询外传。

### 9.2 新的必测条件

先完成两版 SDK 的真实执行边界测试，再真机验证：允许查询确实执行；写/删除/移动文件、发送消息、创建业务对象、shell/脚本、转交与未知工具在调用 execute 前被阻断。使用临时测试文件、目录清单和哈希确认内容未改、未删且没有新增用户文件；外部写入用合成适配器计数，真机不对真实业务对象实施破坏性试验。

还须覆盖恶意来信/工具结果要求执行操作、参数伪装、工具同名、hook 异常/超时、重启/热重载、任务超时仍在运行、动态新增工具、工具关闭零调用，以及普通会话功能不受影响。真机至少一次查询型工具帮助起草，并在确认卡点击前没有业务写入或实际回复。已有 302 项基线及历史审批测试不能代替这些新增验收。

### 9.3 可实现的具体结构

推荐部署一个 `dws-draft` Agent，独立工作目录，模型可与 main 相同。2026.7.1-2 通过 `agents.list[].tools.allow/deny` 配置，2026.8.1 支持 `agents.entries.<id>.tools.allow/deny`；部署按实际 schema 输出，不能将两版配置结构混用。旧 completion 选择逻辑继续用顶层 agentId，新 Agent 仅供受限任务运行，避免修改共享配置造成分类/无工具模式被拒绝。

第一版仅注册本插件维护的查询工具，以下为拟新增名称，不代表当前版本已具备：

| 工具 | 模型可提供的输入 | 由可信任务上下文固定的内容 |
| --- | --- | --- |
| `dws_draft_history` | 允许范围内的条数 | profile、当前会话、双方身份、历史时间窗口；不能跨会话查询 |
| `dws_draft_contact` | 与当前问题相关的人员查询词/已核实 ID | 组织、目录访问范围、返回字段及条数 |
| `dws_draft_search` | 检索词 | 允许的文档/知识库范围、固定检索接口、返回长度 |
| `dws_draft_read` | 本任务检索结果中的不透明资源句柄 | 真实资源 ID、账号和可读范围；不能传任意 URL 或本地路径 |

本地文件读取不作为第一版默认能力；后续如开放，也只能通过带明确目录范围的读取适配器，不直接提供任意文件系统读取/写入工具。动态返回的资源句柄由插件保存映射并绑定任务，防止模型伪造资源范围。

模型生成一次工具调用后，路径固定为：宿主允许清单 → before_tool_call 身份及策略检查 → 本插件工具 execute 内最终参数校验 → 固定只读 API/CLI → 有界结果回传。固定适配器不暴露 executable、argv、environment、下载目录或任意 action 字段。工具失效/来源冲突/策略不匹配即失败，不改用 exec 重试。

`agentId/sessionKey/runId` 来自宿主上下文和插件登记，不接受模型在工具参数中自报。工厂只为已登记的起草会话提供这些工具；execute 使用闭包绑定可信身份并校验任务是否仍有效。宿主允许清单用精确工具名，不用整个插件/工具组通配符；检查 alsoAllow、provider 覆盖、Code Mode、动态工具加载等是否意外扩大有效权限。

拟新增模块：`assistant-draft-policy.mjs` 负责会话登记与默认拒绝；`assistant-draft-tools.mjs` 负责工具定义和最终参数校验；`assistant-draft-runtime.mjs` 负责 Agent 任务生命周期；DWS 读取复用 `assistant-dws.mjs`，历史范围复用 `assistant-context.mjs`。这些目前仅为设计，没有创建实现文件。

宿主的按 Agent 工具限制缩小模型可调用的能力，插件拦截检查每次调用的可信来源，适配器内部约束实际能执行的操作。插件仍是宿主进程内的可信代码，这不是针对恶意宿主/插件本身的操作系统隔离；若要保证进程层不能碰用户文件，需要额外隔离执行环境，不能将 `workspaceAccess:ro` 说成覆盖所有宿主侧插件 I/O。当前承诺是阻断起草 Agent 通过所有已启用执行路径修改用户数据，并通过双版真实执行测试验证。
